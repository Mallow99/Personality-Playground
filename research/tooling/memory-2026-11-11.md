# Tools and memory research for the Best Friend Initiative

Researched 11 November 2026. This is a curated landscape and evaluation plan based on current official documentation, upstream source files, and BFI's architecture and handoff. It is not an exhaustive directory. No candidate was installed, benchmarked on your PC, or connected to your private conversations during this research. Recommendations and complexity judgments are my assessment; feature descriptions are linked to their sources.

**My recommendation is to keep BFI's existing handler, give it a replaceable memory interface, and compare Mem0 and Hindsight against a small local baseline.** Honcho deserves a separate companion-focused trial. Keep Letta as an alternative agent runtime to study. Add voice, media generation, and training through separate services as their requirements become concrete.

**BFI already provides useful foundations.** Its architecture describes Python/FastAPI, SQLite conversation storage, a replaceable inference adapter, bounded tools, and a browser interface. It currently limits generation to one request at a time. Cross-session fact memory, automated model lifecycle, training, voice, and general computer control remain separate work. The handler currently restricts inference endpoints to loopback; adding hosted models requires a deliberate provider adapter, not merely changing a URL. Sources: [architecture](https://github.com/Mallow99/Personality-Playground/blob/work/docs/architecture.md), [dependencies](https://github.com/Mallow99/Personality-Playground/blob/work/pyproject.toml).

The latest [handoff](https://github.com/Mallow99/Personality-Playground/blob/work/docs/HANDOFF.md) records that the v5 visual result was rejected. Earlier passing checks and completion notes do not supersede that decision. Existing technical integration remains useful. This is a concrete requirement for memory and evaluation: preserve evidence, user decisions, and revision history separately. This research makes no changes to the paused artwork.

**What memory needs to mean in BFI**

| Information | Example | Proposed treatment |
| --- | --- | --- |
| Conversation history | What you and a character actually said | Original messages with dates and speaker identity |
| Facts and preferences | Preferred workflow or confirmed hardware | Searchable records with sources, corrections, and current/superseded status |
| Project knowledge | Specs, code, decisions, coursework | Versioned sources and retrieval with file/page references |
| Character identity | Voice, values, interests, personality direction | Explicit behavior specification, separate from remembered events |
| Character experience | What Academic worked on with you | Character-scoped events, plus explicitly shared knowledge |
| Learned procedures | A successful way to run a project check | Reviewed reusable instructions or skills with provenance |
| Working state | What an interrupted task was doing | Persisted task state/checkpoints where needed |

A vector database supplies similarity search. An agent framework supplies execution and state management. A memory service may extract, update, consolidate, and retrieve information. Fine-tuning changes model weights. Installing one does not supply all the others.

**How I would choose**

Start with the baseline, Mem0, and Hindsight on the same dataset. Mem0 is my first integration candidate because BFI already has a Python handler and tool loop. Hindsight is my first comparison because it bundles more retrieval and consolidation machinery. Give Honcho a separate experiment with one user and three character peers, focused on what each knows and how that knowledge changes.

These compete for the main memory responsibility. Installing several simultaneously creates questions about who owns a fact, resolves a correction, or deletes a derived summary. Keep one authoritative source/decision record and make generated indexes rebuildable. Switching providers should become an evaluated export/import exercise rather than an application rewrite.

Pin embedding dimensions/versions; changing them can require reindexing. Reranking adds runtime and dependencies. Similarity does not establish truth.

**The memory contract I would use**

Whatever provider wins, BFI needs explicit remember, recall, correct, forget, inspect, and export operations. Its records should retain:

- Original source, speaker, date, project, and conversation reference.
- Whether a statement is your confirmed decision, character experience, assistant suggestion, or inference.
- Current, superseded, rejected, uncertain, or time-limited status.
- Which characters/projects may retrieve it, enforced by application queries.
- Replacement history and the evidence retrieved for each reply.
- Derived summaries, embeddings, and caches that need invalidating after changes.

Use shared owner preferences, project spaces, and character-specific experience spaces. These are access rules, not personality-prompt promises. Background consolidation needs a resource budget and must not promote guesses to confirmed facts. Learning in a memory product generally means updating stored representations/instructions, not training model weights.

Define forgetting's scope. Deleting an embedding is insufficient if a fact remains in summaries or is extracted again from an old transcript. Align deletion/reingestion behavior with retention rules; backups need clear retention too. Export sources/decisions in a documented ordinary format so changing vendors does not strand project history.

**A fair pilot**

Use synthetic or explicitly selected examples before bulk private imports. Give candidates the same sources, questions, model access, and context budget. Separate retrieval errors from final answering-model errors. Compare with/without optional reranking and include the small baseline.

| Test | Expected behavior |
| --- | --- |
| Restart | Saved preference survives shutdown/restart |
| Correction | Current corrected fact is used; history remains inspectable |
| Visual decision | Retrieve v5 rejection despite older passing-check notes |
| Evidence versus approval | Recognize passing tests did not establish your approval |
| Private character experience | Academic cannot retrieve a private Hacker event without sharing permission |
| Shared preference | All permitted characters receive same current preference |
| Multi-session evidence | Connect a decision and reason across sessions |
| Unknown answer | Admit insufficient evidence rather than invent memory |
| Rejected suggestion | Do not present an assistant proposal as your decision |
| Forget/reingest | Forgotten item does not return from summaries/replay |
| Export/restore | Sources and decisions rebuild useful memory on fresh instance |
| Voice plus memory | Retrieval/consolidation does not make speech unusably slow |

Measure correctness/source support, stale/wrong-memory rate, character isolation, retrieval and first-response latency, ingestion throughput, RAM/VRAM, tokens, and hosted cost if any. Repeat important cases to expose nondeterminism. Correction, isolation, and deletion are required behaviors rather than weaknesses to average away in one score.

[LongMemEval](https://github.com/xiaowu0162/LongMemEval) offers useful evaluation concepts: updates, time, multi-session evidence, and abstention; maintainers also link V2. Published vendor scores are leads, but models/prompts/budgets/dataset versions differ. This report does not declare a speed or accuracy winner from those numbers.

**Practical sequence**

1. Preserve handler and source history. Define memory scopes, corrections/deletion, and acceptance examples. Keep decisions readable in existing documents.
2. On the PC, establish one real local model and actual tools. Record versions, peak memory, and latency before background services.
3. Compare baseline, Mem0, and Hindsight through the same boundary. Trial Honcho peer perspectives if valuable. Select one main memory owner.
4. Add documents and selected retrieval components. Provide memory inspection/correction with source links.
5. Prototype LiveKit or Pipecat with measured speech components. Link speaking/listening to existing avatar tools.
6. Add ComfyUI and training as separately scheduled workloads. Test concurrency/swapping after one-character path is reliable.

Requirements, evaluation examples, provider design, source organization, and dataset curation can happen now. Exact compatibility, memory/latency, simultaneous models/swaps, native overlay, and training capacity need the PC. Availability while the PC is off needs an always-on machine or hosted service. A chat plugin does not itself host BFI or keep background processes alive.

The initial stack I recommend is the existing handler/SQLite, one measured runtime, one memory approach, source-aware retrieval, and visible traces. Voice and media can join through defined interfaces as their tests pass.
